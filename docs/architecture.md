# Go Todo API 学習ガイド

## 目的

GoでTodo APIを**フルスクラッチ・手書き**で作り、次を身につける。

- `net/http` 標準だけでWebサーバを組む方法（フレームワーク・ORMは使わない。DBは `database/sql` で生SQL）
- ヘキサゴナルの最小形（入口と出口の2境界）と、痛みが出た場所にだけ層を足していく判断
- Goらしいinterfaceの切り方（利用側が定義し、実装側は暗黙的に満たす。必要になるまで切らない）
- 集約（一緒に整合性を守る範囲）を境界にしてパッケージ・Repository・Service を切る判断

ゴールは設計の「正解」を暗記することではなく、**なぜその構造にするのかを自分の言葉で説明できるようになること**。

---

## 設計思想

守りたいのは次の3つだけ。形はこれを守るための手段であって目的ではない。

- ライフサイクルが同じものを一箇所に集約する
- 複雑性を局所化する
- 知識を漏らさず、必要最低限のインターフェースで通信する

枠組みはヘキサゴナル（Ports and Adapters）。主張は「コアは外界を知らない、依存は外から内へ」の1点で、これ自体はタダ。境界を明示する費用は、差し替え・テスト・ずれの吸収で回収できる場所にだけ払う。

```txt
最初から固定する（後から変えると高い）:
  HTTP 境界（adapter/web）、Repository を集約単位で分ける、パッケージの依存方向

しんどくなったら足す（後から変えても安い）:
  Service、interface、エンティティのメソッド、Service の分割、Query の分離
```

Clean Architecture や DDD は採用するものではなく、痛みが出たときに必要な部分だけ使う道具。学習用なので痛みは意図的に作り、素朴な状態を一度経験してから導入する。何かを足したら「何が痛かったか、何を足したか、事前に切っておくべきだったか」を一行メモする。

構造は複雑さのある場所に置く。複雑さが通信にあるシステム（中継サーバーなど）にはこの構成を当てはめない。

## 構成

```txt
adapter（外界との接続） → feature（コア：ルール + 段取り + 永続化）
```

| 役割 | 責務 | 置き場 |
| --- | --- | --- |
| Handler | HTTPの入出力、形式バリデーション、ドメインエラー → ステータスコードの翻訳。Service が無い間は段取りもここ | `internal/adapter/web` |
| Repository | 集約の保存・取得。SQL はここだけ | `internal/<feature>/repository.go` |
| エンティティ | 状態遷移と不変条件 | `internal/<feature>/<集約>.go` |
| Service | ユースケースの段取りと tx。必要になってから切る | `internal/<feature>/service.go` |

- **Feature は業務領域で切る**。集約を複数含んでよい（Todo と Tag は同じ `todo/`）
- **集約の見分け方**：「A が無くても B は存在できるか」「B の変更は1回で全 A に効くか」が両方 Yes なら別集約
- **Repository だけは最初から集約ごとに分ける**。束ねると「1回の Save で複数集約を書く」実装が紛れ込むため
- 複数 Feature で共有する外部クライアントや、共通化したくなった Repository 実装は `adapter/` に出す
- `main.go` は起動と配線だけ

## 判断の指針

迷ったら「戻すのが安い方」を選び、隣と揃える。

- **依存は `adapter → feature` の一方向**。HTTP の概念はコアに持ち込まず、SQL は Repository の外に出さない。tx を知っていいのは段取りを持つ層まで
- **Service を切るのは**、1操作で複数 Repository を1 tx で触る／入口が2つになる／段取り自体にルールがある／同じ段取りが重複し始めた、のどれか。一言で言えば「ハンドラに、読む・検証する・呼ぶ・書く、以外の行が出たら」
- **ルールは所有するものに置く**。最初はハンドラに直接書き、散って辛くなったらエンティティのメソッドへ。単一エンティティに置けないルールは同パッケージの関数にする（Domain Service という型は作らない）
- **バリデーションは所有する層で**。形式は Handler、意味はルールの置き場。内側は外側が先に弾く前提に立たず `ErrXxx` を返し、Handler が `errors.Is` で翻訳する
- **外向きはリソース指向**。URL と変更される集約のずれは `adapter/web` が吸収する
- **型の分け方**：リクエスト型は `adapter/web` に切る。レスポンス型は `Todo` を借り、外に出したくない項目や JSON の形のずれが出たら `xxxResponse` を切る。Repository との受け渡しも `Todo`。DB の列とずれたときだけ行用 struct を置く
- **interface は利用側に、必要になるまで切らない**。理由は依存の向き／複数の本物の実装／テストのフェイクの3つだけ。「将来増えるかも」は理由にならない
- **公開は外から触るものだけ**。Feature 内の型名は短く（`todo.Store`）、`adapter/web` は型名がリソースを背負う（`TodoHandler`）

## 学習の道筋（目安）

順番も中身も固定しない。痛みが出る題材を選ぶための目安。

1. **素朴な CRUD**：ハンドラが Store を直接呼ぶ。インメモリ、具体型だけ
2. **差し替え**：インメモリを SQLite にしたくなり、利用側に interface を切る。同じテストを両実装に流す
3. **ドメインを複雑にする**：期限・完了・Priority・タグなどのルールを足す。2集約を1操作で触って Service が、ルールが散ってエンティティのメソッドや Value Object が生まれる
4. **Service を分解する**：ルールが抜けて段取りだけ残った Service を、ユースケース単位や Query に分けるか判断する
5. **複数領域（図書館貸出）**：catalog / membership / lending と worker・通知を足し、領域を跨ぐ tx、入口が2つになること、Repository の `adapter/sqlite` への集約を経験する。コードより先にスキーマと制約を書く

各段階は「単純に作る → 困る → 言語化する → 手法を知る → 導入する → Before / After を比べる」で回す。

## テスト

「何に確信が欲しいか」で3本。モック中心の中間層テストは、段取りにルールが生まれるまで書かない。

- **ドメインのルール**：外部依存なしの単体テスト
- **Repository**：本物の SQLite（インメモリ）に対して。実装が複数あれば同じスイートを流す
- **HTTP の契約**：`httptest` で本物の Store を差し、端から端まで。エンドポイントごとに正常系 + エラー翻訳

## 補足：実務に持ち帰るとき

始め方は学習と同じで、Service や interface は重複・tx・入口の増加が起きてから足す。まとまったリファクタの機会が見込めない組織なら構造を先に作る方が安いが、その場合でも先に作るのは「後から変えると高いもの」だけにする。
